# rs-diag: why asap7_3D fails upper-tier placement with GRT-0029 (19 Nov 2026)

Read from the sources at the recorded commits (Pin-3D 51a19d6f, OpenROAD-Research 305d3ba2), not from a rerun.

**The error.** S2 (gcd) and S3 (ibex) stop in `3_place_upper` on asap7_3D with
`[ERROR GRT-0029] Pin <inst>/<pin> does not have geometries below the max routing layer (M2_m).`
(`record/2026-11-18_s3_v1/flow_logs.tgz`: `flow_logs/asap7_3D/ibex/openroad/3_place_upper.log`, line 230). S2 shows
the same on nangate45_3D.

**Where it comes from.** `place_upper.tcl` runs `global_placement -routability_driven`, which calls the global
router. In OpenROAD-Research 305d3ba2, `src/grt/src/GlobalRouter.cpp` keeps, for each pin of a routed net, only its
routing-layer shapes with `getRoutingLevel() <= max_routing_layer`, and raises GRT-0029 if none are left.

**Why every upper-tier pin trips it.**

| | asap7_3D | asap7_nangate45_3D (passes) |
|---|---|---|
| Tech LEF in use | `asap7_tech_1x_2A6M7M_hbrdl.lef` (ASAP7_HBT_RDL = 1, the default since b55050a) | `asap7_nangate45_2A6M10M.lef` |
| Routing stack, bottom to top | M1 ... M7, HBM_B, hb_layer, HBM_T, M6_m ... M2_m, **M1_m** | M1 ... M10, hb_layer, M6_m ... M2_m, M1_m, **M2_add, M3_add** |
| MIN / MAX_ROUTING_LAYER (`config.mk`) | M2 / **M2_m** | M2 / **M3_add** |
| Upper-tier cell pins (`lef_upper`, e.g. TIELOx1, INVx1, DFFHQNx1 `_upper`) | M1_m only (the DFF has one more shape, on M2_m) | M1_m |
| Upper pins at or below the max layer | no: M1_m is above M2_m | yes: M1_m is below M3_add |

The upper tier is mirrored, so its M1_m is the top of the stack. With the max layer at M2_m, any routed net with an
upper-tier pin fails, whichever pin the router meets first (gcd: a DFF clock pin; ibex: `_39526_/L`, a tie output).
The 2A6M7M (non-RDL) LEF has the same order, so the HBT RDL switch is not the cause. Pin-3D knows M1_m is outside
the range: nangate45_3D's `config.mk` sets `PIN3D_GRT_RELOAD_MAX_ROUTING_LAYER ?= M1_m` ("M1_m is intentionally
outside the M2-M2_m global-routing range"), but only `detail_route.tcl` reads it, after the failing step.

The earlier lead (instances keeping a bottom-tier master) is ruled out: bottom-tier pins are on M1, below the max.

**Candidate fix, untested:** `MAX_ROUTING_LAYER=M1_m` for asap7_3D, which makes its range match what
asap7_nangate45_3D already routes (every layer from M2 up, M1_m included; M1_m has tracks in
`make_tracks.2A6M7M_hbrdl.tcl` and RC in `setRC_2A6M7M_hbrdl.tcl`). It lets the router use M1_m for wires, which the
published flow may not do, so a G1 baseline built on it must say so. Checked by S4 (`s4_layer.sh`): gcd, then ibex.
